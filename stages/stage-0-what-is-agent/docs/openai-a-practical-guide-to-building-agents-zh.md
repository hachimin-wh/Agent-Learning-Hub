越来越多的团队开始将大语言模型（LLM）驱动的 agent 部署到生产环境中。但"agent"这个词对不同的人有不同的含义，从简单的 prompt 链到完全自主的系统都有。本文旨在提供一个实用的框架，帮助你理解 agent 是什么、何时应该构建 agent、以及如何构建可靠的 agent。

## 什么是 Agent？

在 OpenAI 的体系中，**agent** 是指能够使用工具、通过多步骤推理和执行来完成目标的 LLM 驱动系统。

这有别于以下概念：

- **单次 LLM 调用**：给定 prompt，直接得到回答——没有工具、没有多步推理。
- **固定工作流**：预定义的步骤序列，LLM 在每步中执行特定任务，但流程本身是硬编码的。
- **Agent**：LLM 自主决定调用哪些工具、以何种顺序调用、何时停止——流程由模型动态决定。

一个简单的心智模型：**Agent = LLM + 工具 + 循环（loop）**。

## 第一步：判断是否真的需要 Agent

在开始构建之前，先回答一个关键问题：**这个任务是否真的需要 agent？**

Agent 引入了显著的复杂性——更多的 LLM 调用意味着更高的延迟、更高的成本和更多出错的可能。在以下情况下，你通常**不需要**agent：

| 场景 | 更简单的替代方案 |
|---|---|
| 答案可以直接从知识库中检索 | 使用 RAG（检索增强生成） |
| 流程步骤固定且可预定义 | 使用普通代码编排的 chain/workflow |
| 只需要分类或提取信息 | 单次 LLM 调用 + 结构化输出 |
| 任务不需要工具或外部交互 | 单次 LLM 调用 |

**构建 agent 的合理信号**：
- 任务需要的步骤数量在事前无法确定。
- 需要组合使用多种工具，且工具的选择取决于中间结果。
- 任务需要模型"自己想办法"——即基于环境反馈动态调整策略。
- 你已经尝试了更简单的方案，但效果不够好。

## Agent 的核心组件

### 1. 模型（Model）

模型是 agent 的大脑。选择模型时需要考虑：

- **指令遵循能力**：agent 需要严格遵循系统指令，包括何时调用工具、如何格式化输出。
- **推理能力**：复杂任务需要模型能够分解问题、规划步骤、处理歧义。
- **工具调用能力**：模型需要原生支持 function calling / tool use，并能可靠地生成格式正确的工具调用参数。

模型的选择应根据任务复杂度进行梯度匹配——简单任务用更快/更便宜的模型（如 GPT-4o mini），复杂推理任务用更强模型（如 GPT-4o 或 o 系列）。

### 2. 工具（Tools）

工具是 agent 与外部世界交互的接口。常见工具类型：

| 工具类别 | 示例 |
|---|---|
| **检索工具** | 搜索知识库、查询数据库、网页搜索 |
| **操作工具** | 发送邮件、创建工单、更新 CRM 记录 |
| **计算工具** | 代码执行、数学计算、数据转换 |
| **感知工具** | 读取文件、截图、API 调用 |

**工具设计原则**：

- **描述清晰**：模型通过读取工具的名称、描述和参数 schema 来决定调用哪个工具。描述模糊 = 调用错误。
- **接口简单**：每个工具只做一件事。复杂的操作应该拆分为多个工具，而不是一个"万能"工具。
- **返回结构化结果**：工具返回的信息应该结构化（如 JSON），并包含明确的成功/失败指示——错误信息比静默失败更有用。
- **提供足够的上下文**：工具返回的结果应包含 agent 下一步决策所需的信息（例如，搜索结果应包括标题、摘要、来源 URL）。

### 3. 编排层（Orchestration）

编排层是 agent 的"循环引擎"，负责：

- 管理对话历史和上下文窗口
- 执行"模型输出 → 解析工具调用 → 执行工具 → 将结果输入模型"的循环
- 实现停止条件（最大步数、超时、成本上限）
- 处理错误（工具调用失败、模型输出格式错误、超时重试）

**编排模式的选择**：

```
单 Agent 循环                多 Agent（编排器模式）
┌──────────┐                ┌──────────────┐
│  Model   │                │ Orchestrator │
│  ↕       │                │  (Planner)   │
│  Tools   │                └──┬───┬───┬──┘
└──────────┘                  ↓   ↓   ↓
                         ┌────┐ ┌────┐ ┌────┐
                         │ A1 │ │ A2 │ │ A3 │
                         └────┘ └────┘ └────┘
```

对于大多数应用，从单 agent 开始。只有当单一 agent 的上下文变得过于庞大，或者任务天然需要不同"专业角色"并行工作时，才引入多 agent 编排。

## Agent 开发流程

### 阶段 1：原型设计（Prototype）

1. **从最简单的实现开始**：用最少的代码实现 agent 循环——一个 while 循环、一个 LLM 调用、一个工具执行器。
2. **手动跑通几个端到端案例**：不要先写评估框架。先用几个真实输入手动测试，观察 agent 的行为是否符合预期。
3. **迭代 prompt 和工具描述**：这是 agent 开发中投入产出比最高的环节。一个好的工具描述往往比复杂的编排逻辑更有价值。

```python
# 最小 agent 循环伪代码
messages = [{"role": "system", "content": SYSTEM_PROMPT},
            {"role": "user", "content": user_query}]

for step in range(MAX_STEPS):
    response = llm.chat(messages, tools=TOOLS)
    
    if response has no tool_calls:
        return response.content  # Agent 认为任务完成
    
    for tool_call in response.tool_calls:
        result = execute_tool(tool_call)
        messages.append(tool_call_result(result))
```

### 阶段 2：评估（Evaluation）

一旦原型能跑通几个案例，就需要建立系统化的评估：

- **测试集**：收集 20-50 个真实场景的输入-期望输出对。这些用例应覆盖常见路径和边缘情况。
- **评估维度**：
  - 任务完成率（是否达到目标）
  - 工具选择准确率（是否调用了正确的工具）
  - 效率（完成任务所需的步骤数、token 消耗）
  - 安全性（是否执行了危险操作）
- **评估方法**：
  - 对于有明确正确答案的任务：直接比对输出
  - 对于开放式任务：使用 LLM-as-judge（用另一个 LLM 根据评分标准打分）
  - 对于关键任务：人工抽查

### 阶段 3：安全与护栏（Safety & Guardrails）

Agent 因能自主执行操作，安全风险比普通 LLM 应用更高：

| 风险类别 | 示例 | 缓解措施 |
|---|---|---|
| **不当操作** | agent 误删数据、发送错误邮件 | 危险操作需要人工确认；操作需有撤销机制 |
| **提示注入** | 用户通过巧妙措辞绕过限制 | 输入过滤；将用户输入和系统指令严格隔离 |
| **循环失控** | agent 陷入无限循环，持续消耗 token | 设置硬性上限：最大步数、超时、成本上限 |
| **数据泄露** | agent 将敏感信息发送到外部 API | 工具层面做数据脱敏；审计日志 |
| **幻觉操作** | agent 基于错误假设执行操作 | 关键操作前要求 agent 明确陈述假设并等待确认 |

### 阶段 4：部署与监控（Deployment & Monitoring）

生产环境中的 agent 需要：

- **日志与可观测性**：记录每次 LLM 调用的 prompt、响应、工具调用和工具结果。当 agent 行为异常时，你需要完整的 trace 来定位问题。
- **速率限制与成本控制**：设置每用户/每会话的调用上限和预算上限。
- **降级策略**：当 agent 无法完成任务时，应有优雅的降级方案——比如转人工客服。
- **持续评估**：定期用测试集回归测试，确保模型更新或 prompt 修改不会导致能力退化。

## 常见陷阱

1. **过度工程化**：在简单的 prompt 就足够时引入了复杂的 agent 框架。
2. **工具定义不清晰**：模型无法正确选择工具，因为描述模糊或参数名不直观。
3. **没有停止条件**：agent 在迭代中迷失，不断调用无关工具。
4. **上下文爆炸**：没有及时清理历史记录，导致上下文窗口溢出，agent 丢失早期信息。
5. **忽视评估**：仅凭几个 demo 就认为 agent "工作正常"，没有系统化的测试集。

## 总结：构建 Agent 的检查清单

在开始构建之前：
- [ ] 确认任务确实需要 agent（而非更简单的方案）
- [ ] 定义了清晰的成功标准

在开发过程中：
- [ ] 从最简单的实现开始——手动跑通几个案例
- [ ] 迭代优化 prompt 和工具描述（这是最大的杠杆点）
- [ ] 设置硬性护栏：最大步数、超时、成本上限
- [ ] 建立系统化的测试集和评估流程

在上线之前：
- [ ] 危险操作需要人工确认
- [ ] 日志和 trace 完备
- [ ] 有降级策略
- [ ] 通过回归测试

Agent 开发的本质不是堆砌框架，而是**对 LLM 行为的深度理解和精心设计的人机交互界面**。从简单开始，用评估驱动迭代——这是构建可靠 agent 最务实的路径。
